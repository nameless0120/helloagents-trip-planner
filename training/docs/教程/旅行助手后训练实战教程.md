# 旅行助手后训练实战教程

这份教程按当前代码整理。读者从项目根目录开始，用一个总入口完成数据生成、审计、导出、校验，并按需接到 SFT、DPO 和评测。

## 一眼看懂流程

```text
准备环境和 API Key
  -> preflight
  -> 请求分布检查
  -> PlannerContext 检查
  -> SFT 数据生成
  -> 预算审计和可用性分类
  -> LLaMA-Factory 数据导出
  -> TripPlan 格式校验
  -> SFT 训练
  -> Best-of-N 数据增强 / 多候选 rerank
  -> DPO 数据生成（可选）
  -> 评测（可选）
```

总入口是：

```text
training/scripts/run_pipeline.py
```

底层 SFT 生成脚本是：

```text
training/scripts/planner/data/generate_sft_data.py
```

## 1. 准备环境

在项目根目录创建训练环境：

```bash
python3 -m venv .venv-training-py311
source .venv-training-py311/bin/activate
python -m pip install -r training/requirements-training.txt
```

训练数据生成至少需要在 `backend/.env` 或项目根 `.env` 中配置：

```bash
AMAP_MAPS_API_KEY=your_amap_api_key
DATA_GEN_API_KEY=your_data_generation_key
DATA_GEN_BASE_URL=https://api.deepseek.com
DATA_GEN_MODEL=your_model_name
DATA_GEN_THINKING=false
```

`DATA_GEN_THINKING=false` 是当前默认口径。此时数据生成请求不会携带思考参数，模型直接返回用于解析的 JSON。

如果只做请求分布 dry-run，可以不配置 API Key；PlannerContext smoke 需要高德 Key；正式 SFT 还需要数据生成模型 Key。

## 2. 先做不联网检查

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage preflight \
  --strict-preflight
```

只想查看会执行哪些命令，在任意正式命令末尾加：

```bash
--dry-run
```

`--dry-run` 不调用 API、不写训练数据、不启动 GPU 训练。

## 3. 检查请求和上下文

请求分布检查不调用外部服务：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft-request \
  --count 20 \
  --request-source controlled \
  --date-mode mixed
```

PlannerContext 检查会调用高德，但不会调用数据生成模型，也不会写训练 records：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft-context \
  --count 20 \
  --request-source controlled \
  --date-mode mixed \
  --workers 1
```

这一步重点看酒店、景点、餐饮、天气、价格 hint 和预算策略是否完整。

## 4. 固定本轮路径

后面的主命令会复用这些变量：

```bash
export RUN_NAME="$(date +%Y%m%d_%H%M%S)_reader"
export SFT_RUN="training/data/planner/sft_runs/${RUN_NAME}"
export SFT_DATASET="trip_planner_sft_${RUN_NAME}"
export BESTOFN_RUN="training/data/planner/bestofn/${RUN_NAME}"
export BESTOFN_DATASET="trip_planner_bestofn_${RUN_NAME}"
export DPO_RUN="training/data/planner/dpo/${RUN_NAME}"
export DPO_DATASET="trip_planner_dpo_${RUN_NAME}"
```

## 5. 数据生成

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft-data \
  --count 20 \
  --request-source controlled \
  --date-mode mixed \
  --workers 1 \
  --sft-dir "$SFT_RUN"
```

这一步调用高德和数据生成模型，输出 `$SFT_RUN/records.jsonl`。失败请求和原因会写到 `$SFT_RUN/errors.jsonl`。

## 6. 数据审计

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft-audit \
  --records "$SFT_RUN/records.jsonl" \
  --sft-dir "$SFT_RUN" \
  --sft-dataset-prefix "$SFT_DATASET"
```

总入口会按下面顺序执行：

```text
audit_sft_budget_fit.py
  -> classify_sft_budget_usability.py
  -> export_sft_budget_clean_subset.py
  -> validate_trip_plan.py
```

本轮输出在 `$SFT_RUN`，主要文件是：

```text
records.jsonl                 # 成功生成的完整记录
errors.jsonl                  # 失败请求和错误原因
audit_budget/                 # 预算审计
classification/              # 样本可用性分类
export_budget_clean/          # 通过审计的完整 records 子集
pipeline_manifest.json        # 本轮参数
```

通过审计的 train/val 文件写入：

```text
training/data/llamafactory/generated/
```

并同步登记到 `training/data/llamafactory/dataset_info.json`。数据集名是 `${SFT_DATASET}_train` 和 `${SFT_DATASET}_val`。

## 7. SFT 微调

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage train \
  --config training/configs/qwen25_7b/sft_qwen25_7b_lora.yaml \
  --train-dataset "${SFT_DATASET}_train" \
  --train-eval-dataset "${SFT_DATASET}_val" \
  --llamafactory-root ../LLaMA-Factory \
  --train-output-dir training/outputs/qwen25_7b/sft
```

这一步只训练，不会重新生成数据。`train` 阶段会占用 GPU；确认命令时加 `--dry-run`。

## 8. Best-of-N 数据增强和产品侧 rerank

Best-of-N 不是旧流程。最终多候选 rerank 确实有用，所以当前仓库保留两部分：

- 训练侧：用 `run_pipeline.py --stage bestofn` 生成多候选、规则选择，并导出新的 SFT / DPO 数据。
- 产品侧：后端 `backend/app/planner/rerank.py` 会对多次生成的合法 `TripPlan` 候选重新打分，选更稳的一条返回。

历史报告里的日期化 shell 脚本只代表当时那轮实验怎么跑，不再作为读者入口。现在要复现 Best-of-N，从下面这条命令开始。

先启动 SFT 服务：

```bash
.venv-training-py311/bin/python3 training/scripts/serving/manage_planner_service.py \
  start-all \
  --services sft \
  --sft-devices 6 \
  --sft-adapter-path training/outputs/qwen25_7b/sft
```

再生成候选并导出数据：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage bestofn \
  --records "$SFT_RUN/export_budget_clean/records.jsonl" \
  --bestofn-dir "$BESTOFN_RUN" \
  --bestofn-dataset-prefix "$BESTOFN_DATASET" \
  --bestofn-base-url http://127.0.0.1:4396/v1 \
  --bestofn-api-model trip-planner-sft \
  --bestofn-spec t02:0.2:1 \
  --bestofn-spec t05:0.5:2 \
  --bestofn-spec t08:0.8:1 \
  --workers 1
```

输出会写到 `$BESTOFN_RUN`，并登记四个数据集：

```text
${BESTOFN_DATASET}_sft_train
${BESTOFN_DATASET}_sft_val
${BESTOFN_DATASET}_pair_train
${BESTOFN_DATASET}_pair_val
```

如果要继续做 Best-of-N replay SFT，把第 7 节训练命令里的数据集名换成 `${BESTOFN_DATASET}_sft_train` 和 `${BESTOFN_DATASET}_sft_val`。

后端多候选 rerank 默认开启：

```bash
PLANNER_ENABLE_RERANK=1
PLANNER_RERANK_CANDIDATE_COUNT=3
PLANNER_RERANK_TEMPERATURE_STEP=0.08
```

这部分不是训练脚本，而是线上 Planner 生成时的候选选择逻辑。

## 9. DPO 数据和训练

DPO 使用审计后的 SFT records 生成候选，再构造 chosen/rejected pair：

```text
SFT clean records
  -> dpo_build_prompts.py
  -> dpo_generate_candidates.py
  -> dpo_judge_candidates.py
  -> dpo_build_pairs.py
  -> dpo_audit_pairs.py
  -> LLaMA-Factory DPO
```

先启动 base 和 SFT 服务：

```bash
.venv-training-py311/bin/python3 training/scripts/serving/manage_planner_service.py \
  start-all \
  --services base,sft \
  --base-devices 4,5 \
  --sft-devices 6 \
  --sft-adapter-path training/outputs/qwen25_7b/sft
```

然后生成 DPO 数据并训练：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage dpo \
  --stage train \
  --records "$SFT_RUN/export_budget_clean/records.jsonl" \
  --dpo-dir "$DPO_RUN" \
  --dpo-dataset-prefix "$DPO_DATASET" \
  --dpo-workers 1 \
  --judge-workers 1 \
  --config training/configs/qwen25_7b/dpo_qwen25_7b_lora.yaml \
  --llamafactory-root ../LLaMA-Factory \
  --train-output-dir training/outputs/qwen25_7b/dpo
```

DPO 需要可访问的 Base/SFT 模型服务和 judge 配置。先用 `--dry-run` 检查路径与命令，不会请求模型服务。

## 10. 评测

DPO 训练完成后，启动 DPO 服务：

```bash
.venv-training-py311/bin/python3 training/scripts/serving/manage_planner_service.py \
  start-all \
  --services dpo \
  --dpo-devices 7 \
  --dpo-adapter-path training/outputs/qwen25_7b/dpo
```

然后跑冻结评测集：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage eval \
  --records training/data/planner/eval/records.jsonl \
  --model-name trip_planner_dpo \
  --api-model trip-planner-dpo \
  --base-url http://127.0.0.1:4398/v1 \
  --eval-dir training/outputs/eval/dpo \
  --workers 1
```

评测会生成模型输出并计算 schema、日期、天气、候选 grounding、餐饮、酒店和预算指标。模型服务不可用时，用 `--dry-run` 先检查命令。

只做格式校验：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage validate \
  --validate-sft training/data/llamafactory/generated/<sft_train>.json
```

## 11. `party` 字段问题从哪里看

当前请求 schema 在 `backend/app/models/schemas.py`，PlannerContext 组装在 `backend/app/planner/`，SFT 入口在 `training/scripts/planner/data/generate_sft_data.py`。

`party` 属于请求和 PlannerContext 的结构化字段，至少要包含 `adults`、`children`、`elders`、`total` 和 `companion_type`。模型输出仍然按 `TripPlan` schema 校验，不要把请求字段直接拼进模型输出。

如果直接运行底层脚本遇到 `party` 校验错误，先运行：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft-data \
  --count 3 \
  --request-source controlled \
  --date-mode mixed \
  --workers 1 \
  --dry-run
```

确认总入口实际调用的是 `planner/data/generate_sft_data.py`。正式生成后，查看该 run 的 `records.jsonl`、`errors.jsonl` 和 `pipeline_manifest.json`。当前仓库不再提供另一套 SFT 生成入口。
