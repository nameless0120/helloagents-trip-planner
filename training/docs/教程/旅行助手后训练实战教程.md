# 旅行助手后训练实战教程

这份教程按当前代码整理。读者从项目根目录开始，用一个总入口完成数据生成、审计、导出、校验，并按需接到 SFT、DPO 和评测。

## 一眼看懂流程

```text
准备环境和 API Key
  -> preflight
  -> 请求分布检查
  -> PlannerContext 检查
  -> SFT 数据生成
  -> 预算审计和可用性分类
  -> LLaMA-Factory 数据导出
  -> TripPlan 格式校验
  -> SFT 训练
  -> DPO 数据生成（可选）
  -> 评测（可选）
```

总入口是：

```text
training/scripts/run_pipeline.py
```

底层 SFT 生成脚本是：

```text
training/scripts/planner/data/generate_sft_data.py
```

## 1. 准备环境

在项目根目录创建训练环境：

```bash
python3 -m venv .venv-training-py311
source .venv-training-py311/bin/activate
python -m pip install -r training/requirements-training.txt
```

训练数据生成至少需要在 `backend/.env` 或项目根 `.env` 中配置：

```bash
AMAP_MAPS_API_KEY=your_amap_api_key
DATA_GEN_API_KEY=your_data_generation_key
DATA_GEN_BASE_URL=https://api.deepseek.com
DATA_GEN_MODEL=your_model_name
DATA_GEN_THINKING=false
```

`DATA_GEN_THINKING=false` 是当前默认口径。此时数据生成请求不会携带思考参数，模型直接返回用于解析的 JSON。

如果只做请求分布 dry-run，可以不配置 API Key；PlannerContext smoke 需要高德 Key；正式 SFT 还需要数据生成模型 Key。

## 2. 先做不联网检查

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage preflight \
  --strict-preflight
```

只想查看会执行哪些命令，在任意正式命令末尾加：

```bash
--dry-run
```

`--dry-run` 不调用 API、不写训练数据、不启动 GPU 训练。

## 3. 检查请求和上下文

请求分布检查不调用外部服务：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft-request \
  --count 20 \
  --request-source controlled \
  --date-mode mixed
```

PlannerContext 检查会调用高德，但不会调用数据生成模型，也不会写训练 records：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft-context \
  --count 20 \
  --request-source controlled \
  --date-mode mixed \
  --workers 1
```

这一步重点看酒店、景点、餐饮、天气、价格 hint 和预算策略是否完整。

## 4. 生成并审计 SFT 数据

推荐先生成一小批：

```bash
RUN_DIR="training/data/planner/sft_runs/$(date +%Y%m%d_%H%M%S)_reader_smoke"
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft \
  --count 20 \
  --request-source controlled \
  --date-mode mixed \
  --workers 1 \
  --sft-dir "$RUN_DIR"
```

总入口会按下面顺序执行：

```text
generate_sft_data.py
  -> audit_sft_budget_fit.py
  -> classify_sft_budget_usability.py
  -> export_sft_budget_clean_subset.py
  -> validate_trip_plan.py
```

本轮输出在 `$RUN_DIR`，主要文件是：

```text
records.jsonl                 # 成功生成的完整记录
errors.jsonl                  # 失败请求和错误原因
audit_budget/                 # 预算审计
classification/              # 样本可用性分类
export_budget_clean/          # 导出前的审计子集
pipeline_manifest.json        # 本轮参数
```

通过审计的 train/val 文件写入：

```text
training/data/llamafactory/generated/
```

并同步登记到 `training/data/llamafactory/dataset_info.json`。每轮使用新的 `$RUN_DIR`，不要把不同批次混在同一个目录。

## 5. 接到 SFT 训练

确认数据流程通过后，可以在同一个总入口里直接训练：

```bash
RUN_DIR="training/data/planner/sft_runs/$(date +%Y%m%d_%H%M%S)_reader_train"
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft \
  --stage train \
  --count 20 \
  --request-source controlled \
  --date-mode mixed \
  --workers 1 \
  --sft-dir "$RUN_DIR" \
  --config training/configs/qwen25_7b/sft_qwen25_7b_lora.yaml \
  --llamafactory-root ../LLaMA-Factory
```

入口会自动把本轮数据集、验证集和输出目录接给 LLaMA-Factory，不需要手动修改 YAML 或复制数据文件。`train` 阶段会占用 GPU；确认命令时加 `--dry-run`。

## 6. DPO 数据和训练

DPO 使用当前 SFT records 生成候选，再构造合法的 chosen/rejected pair：

```text
SFT records
  -> dpo_build_prompts.py
  -> dpo_generate_candidates.py
  -> dpo_judge_candidates.py
  -> dpo_build_pairs.py
  -> dpo_audit_pairs.py
  -> LLaMA-Factory DPO
```

从已有 SFT records 开始：

```bash
RUN_DIR="training/data/planner/sft_runs/<run>"
DPO_DIR="training/data/planner/dpo/<run>"
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage dpo \
  --records "$RUN_DIR/records.jsonl" \
  --dpo-dir "$DPO_DIR" \
  --dpo-workers 1
```

正式 DPO 训练时，在同一条命令中追加：

```text
--stage train --config training/configs/qwen25_7b/dpo_qwen25_7b_lora.yaml --llamafactory-root ../LLaMA-Factory
```

DPO 需要可访问的 Base/SFT 模型服务和 judge 配置。先用 `--dry-run` 检查路径与命令，不会请求模型服务。

## 7. 评测

评测输入使用仓库中的冻结记录：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage eval \
  --records training/data/planner/eval/records.jsonl \
  --eval-dir training/outputs/eval/<run> \
  --model-name <model_name> \
  --api-model <api_model> \
  --base-url http://127.0.0.1:4396/v1 \
  --workers 1
```

评测会生成模型输出并计算 schema、日期、天气、候选 grounding、餐饮、酒店和预算指标。模型服务不可用时，用 `--dry-run` 先检查命令。

只做格式校验：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage validate \
  --validate-sft training/data/llamafactory/generated/<sft_train>.json
```

## 8. `party` 字段问题从哪里看

当前请求 schema 在 `backend/app/models/schemas.py`，PlannerContext 组装在 `backend/app/planner/`，SFT 入口在 `training/scripts/planner/data/generate_sft_data.py`。

`party` 属于请求和 PlannerContext 的结构化字段，至少要包含 `adults`、`children`、`elders`、`total` 和 `companion_type`。模型输出仍然按 `TripPlan` schema 校验，不要把请求字段直接拼进模型输出。

如果直接运行底层脚本遇到 `party` 校验错误，先运行：

```bash
.venv-training-py311/bin/python3 training/scripts/run_pipeline.py \
  --stage sft \
  --count 3 \
  --request-source controlled \
  --date-mode mixed \
  --workers 1 \
  --dry-run
```

确认总入口实际调用的是 `planner/data/generate_sft_data.py`，并查看该 run 的 `records.jsonl`、`errors.jsonl` 和 `pipeline_manifest.json`。当前仓库不再提供另一套 SFT 生成入口。

## 9. LLaMA-Factory 本地改动

长上下文 DPO 使用项目补丁：

```text
training/patches/llamafactory-9a0cfdcc-local.patch
```

准备 checkout：

```bash
cd ..
git clone https://github.com/hiyouga/LLaMA-Factory.git LLaMA-Factory
cd LLaMA-Factory
git checkout 9a0cfdccfa234304879f83e0c2c17b5ede8121fe
git apply ../helloagents-trip-planner/training/patches/llamafactory-9a0cfdcc-local.patch
cd ../helloagents-trip-planner
.venv-training-py311/bin/python3 -m pip install -e ../LLaMA-Factory --no-deps
```

补丁只改变长上下文 log probability 的计算和 v1 训练评测接口，不改变 DPO 目标函数。完整说明见 [DPO 分块 LogProb 方案](../内部文档/DPO分块LogProb方案说明.md)。
